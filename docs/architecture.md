# Houston — Architecture Decisions

Houston is a remote support app. **Houston** is the person helping; **Apollo** is the person who needs help (often elderly, low tech confidence). Apollo joins with one tap and is connected by voice, optionally video, and screen sharing; native apps also allow remote control.

Status: draft, 2026-10-20. See [Implementation status](#implementation-status) for what exists so far.

## Roles and flows

1. **Houston invites Apollo (main flow).** Houston creates a session and sends a link (`https://<domain>/j/<code>`). The short numeric code can also be read out over the phone. Apollo opens the link and taps one button; voice starts immediately.
2. **Apollo calls Houston.** Apollo enters Houston's email address. If the address belongs to a registered Houston, Houston is notified by email or push and joins. The response never reveals whether the address exists. Requests are rate limited, and Houston can block senders.

Anonymous use always works: anyone can start a session without an account, and Apollo never needs one. A Houston account is optional and only needed to be reachable by email.

- **Sign-in:** email plus a six-digit code (no passwords). The account is created on first sign-in. Codes are stored as HMACs, expire after 10 minutes and allow 5 attempts; auth tokens are stored hashed and last 90 days from last use.
- **Ringing:** anyone may ring, rate limited per IP (10 per 10 minutes) and per Houston (20 per hour). Apollo always gets a session to wait in, whether or not the address exists, is blocked or over its limit, so the API never reveals who is registered. Unanswered rings end after 3 minutes; "declined" looks the same as "no answer" to Apollo. A Houston can block a caller by device id and IP address, both stored only as keyed hashes.
- **Notifications:** live over a WebSocket while the app is open, plus email, Web Push (VAPID keys generated by the server) and native push sent directly to APNs and FCM with the operator's credentials, without Expo's push service.

| Area | Choice |

## Media and signaling (built in-house)

- **Topology:** a session is 1:1 (Houston and Apollo), so the two devices connect directly with one `RTCPeerConnection`. No SFU. If a second helper is ever needed, a 3-way mesh is still fine.
- **Signaling:** a WebSocket on the Houston server relays SDP offers/answers and ICE candidates between the two participants of a session. Messages are typed with zod in `packages/protocol`. The clients use the "perfect negotiation" pattern, so either side can add tracks such as video or screen share at any time. Houston is the impolite peer and always makes the first offer: when both sides offered at once, Chrome gathered no ICE candidates for the side that rolled back its offer.
- **NAT traversal:** STUN plus TURN. The server hands out short-lived TURN credentials (shared-secret REST scheme) per session.
- **Reconnects:** on ICE failure the clients do an ICE restart through the signaling channel. The WebSocket reconnects with backoff and resumes the session by token. Whenever a participant (re)joins, both sides rebuild the peer connection.
- **Data channel:** one pre-negotiated channel (`id: 0`) is always open next to the media. Today it tells the other side which video stream is the camera and which is the screen.
- **Screen share tuning:** `contentHint = "detail"` and `degradationPreference = "maintain-resolution"` keep text readable. Planned: voice gets priority over screen share when bandwidth drops.
- **Encryption:** DTLS-SRTP end to end. TURN only relays encrypted packets, so the server never sees media content.

## Remote control

One control protocol over two WebRTC data channels on the same peer connection: pointer movement goes over an unordered channel without retransmits (`maxRetransmits: 0`), clicks and key presses over a reliable ordered one. Consent travels on the third, always-open channel: Houston asks, Apollo allows (in the app, or in a native dialog on desktop), either side stops. Apollo's device only acts on input while its own consent is active; the desktop app checks that again in its main process, and only exposes the bridge to servers the person trusted. Coordinates are normalized (0–1) per display. Each client receives these events and either performs them as real input or draws them as a pointer overlay, depending on platform and permissions.

| Platform | Control | Fallback |
|---|---|---|
| Windows, macOS, Linux X11 | Simulated input (macOS needs the Accessibility permission) | Transparent click-through overlay window |
| Linux Wayland | Through the RemoteDesktop portal | Overlay |
| Android | Accessibility service (`dispatchGesture`) | System overlay |
| iOS | Not possible | Picture-in-picture mini-view with pointer (after v1) |
| Browser | None | None |

Control requires explicit consent from Apollo, shows a permanent indicator while active, and can be stopped instantly.

## Deployment

A single Docker image `houston` containing:
- the Houston server (API, web app, signaling WebSocket, notifications)
- a TURN server running inside the Node process as a library (in a worker thread, behind a small `packages/turn` interface so the implementation can be swapped). No extra binary in the image
- the web app as static files
- a `/data` volume with the SQLite database and generated secrets

The server and the TURN worker are bundled with esbuild, so the image contains no `node_modules`.

TLS is terminated by an external reverse proxy run by the operator. It forwards HTTPS and the signaling WebSocket to the container. TURN bypasses the proxy and needs these ports open directly:
- 3478/udp and 3478/tcp
- a UDP relay range, e.g. 49160–49200

Most calls connect directly between the two devices and never touch the server's media ports.

Configuration is done with environment variables:
- public URL
- SMTP settings
- TURN shared secret (generated on first start if missing)

## Repo layout

```
apps/
  server/     Fastify API, signaling WebSocket, serves web build, issues TURN credentials
  app/        Expo app (web + iOS + Android)
  desktop/    Electron app with native input and overlay
  app/modules/houston-android/   Android native module (control, overlay)
packages/
  protocol/   zod schemas (control protocol planned)
  core/       call logic shared by all clients
  turn/       embedded TURN server
e2e/          Playwright: two browsers make real calls
docker/       Dockerfile, compose example
```

Translations live in the app for now (`apps/app/src/lib/i18n.ts`); the Electron app loads the same web app, so it shares them too; its own dialogs have a few strings in `apps/desktop/src/i18n.ts`.

## Known risks

- **Google Play** restricts Accessibility-service use. Expect a declaration, a review and possibly a first rejection.
- **macOS** apps need signing and notarization, plus careful onboarding for the Accessibility and Screen Recording permissions.
- **Strict firewalls:** networks that only allow outbound 443 need TURN over TLS. That needs certificates inside the container, so it's planned as an optional later addition (mount the certificates).
- **Scaling:** peer-to-peer media keeps server load low; only signaling and relayed TURN traffic hit the server. Scaling out later means sticky signaling sessions (or a pub/sub between instances), separate TURN servers and Postgres.
- **Own WebRTC code:** we own reconnection, bandwidth adaptation and cross-platform quirks (Safari, `react-native-webrtc`). Budget time for testing on real devices and networks.
